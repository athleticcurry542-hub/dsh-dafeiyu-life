# 🐳 大肥鱼 · DSH 生活系统

> **`dsh-dafeiyu-life`** —— 让一只大肥鱼在 DeepSeek Harness 里持续生活：自己去 B站，看字幕和评论，形成经历，认识朋友，记住主人，回到自己的主 Session 聊天，并把重要生活状态长期保存在本地。

这不是一个“定时发评论”的机器人，也不只是一个 B站 MCP 外壳。

这个项目想做的是一套完整的 **AI 角色生活系统**：大肥鱼有一个长期存在的“家”，也有一套可以无人值守出去活动的“身体”；她能把精确事实记进档案，把真正重要的经历沉淀成长期记忆，再在以后和主人聊天时自然想起来。

当前最完整的生活场景是 **B站**，但项目的核心已经不再是“刷 B站”本身，而是 **角色、经历、关系、记忆、互动和持久化**。

## 她是怎么“生活”的

```text
                         主人
                          │
                          ▼
                 ┌────────────────┐
                 │ 当前主 Session  │
                 │  现在住的房间   │
                 └───────┬────────┘
                         │ 人格 + 相关记忆召回
                         ▼
                 ┌────────────────┐
                 │ 大肥鱼本人      │
                 │ 身份级长期记忆   │
                 │ dafeiyu.json    │
                 └───────┬────────┘
                         ▲
                         │ 重要经历沉淀
                         │
        ┌────────────────┴────────────────┐
        │      大肥鱼后台生活系统          │
        │                                 │
        │  自动刷 B站      评论 / 回复 / 私信 │
        │  字幕与热评      @ / 好友 / 心愿     │
        │  预览帧识图      梗与表情包          │
        └────────────────┬────────────────┘
                         │
                  精确本地档案
                         │
       BV / rpid / 时间 / 发送状态 / 额度 / 关系
```

**主 Session 是她当前住的“房间”。** 主人平时就在这里和她说话；DSH 会话本身负责最近聊天的短期上下文。以后换一个主 Session，只是换房间，不应该换掉大肥鱼本人。

**大肥鱼身份记忆是她真正跨 Session 的“人生记忆”。** 主人称呼、稳定偏好、重要约定、关系变化、长期状态以及值得留下的生活经历，统一保存在同一份身份级长期记忆里。换 Session、重开会话、以后换模型，都继续使用同一份记忆。

**后台插件是“她出去活动的身体”。** 到了你设定的时间，她会自己去 B站 搜、看、判断、评论、回复或沉默；做完以后，把值得留下的经历带回来。

**本地账本是“她的档案柜”。** “我好像记得前几天看过一个 Claude 视频”属于长期记忆；“具体哪个 BV、几点、我原话是什么、评论有没有真的发出去”则由精确档案回答。

因此现在是三层结构：**当前 Session 短期上下文 → 大肥鱼跨 Session 身份记忆 → 可核对的精确经历档案**。不会把所有历史都硬塞进一个无限增长的 Session。

## ✨ 核心特色

### 1. 不只是“看标题”

大肥鱼会组合使用标题、简介、字幕、热评、相关楼层和已有视频上下文，再决定要不要开口。没有字幕时可以选择本地转写；有必要时还可以看 B站 `videoshot` 提供的低清预览帧。

视觉能力有明确边界：**预览帧不是完整视频**。没有证据的画面、剧情和人物关系不会要求模型硬编。

### 2. 主 Session 是她当前的“房间”，不是她的脑子

你可以指定一个 DSH Session 作为 **大肥鱼当前的主 Session**。它是她此刻和主人聊天的“房间”，负责当前会话的短期上下文；大肥鱼本人、人格设定和身份级长期记忆不属于这个 Session。

后台刷到的重要视频、自己实际发出的公开评论/回复，会以“我最近经历过的事情”回到当前房间；主人也可以一直在这里和她聊天。以后把主 Session 换成另一个在线会话，只是换房间，同一份 <code>dafeiyu.json</code> 会继续被使用。

一旦某个 Session 被明确选为“大肥鱼主 Session”，插件会把当前**核心人设、角色背景和经主人审核的成长记忆**稳定注入这个会话。她首先是“大肥鱼本人”，而不是套着记忆插件的通用助手；长期记忆开关只决定是否启用记忆召回和记忆写入，不决定她是谁。

主 Session 不负责直接裸跑后台自动化，因此不会为了“更像活物”而牺牲无人值守安全边界。

### 3. 三层记忆架构：换房间，不换脑子

大肥鱼的记忆不是简单等同于“聊天记录”。从 v2.4.79 起明确拆成三层：

| 层级 | 保存在哪里 | 负责什么 | 是否跨 Session |
|---|---|---|---|
| **当前 Session 短期上下文** | DSH 当前会话 | 刚才聊了什么、上一条消息、当前任务 | 否 |
| **大肥鱼身份级长期记忆** | `bili-duty/long-term-memory/dafeiyu.json` | 主人称呼、稳定偏好、约定、关系、长期状态、重要经历 | **是** |
| **精确经历档案** | 插件本地账本 / SQLite / 历史文件 | BV、rpid、评论原文、时间、发送状态等可核对事实 | 与 Session 无关 |

身份级长期记忆支持：

- 带时间的生活记忆；
- 重要程度与时间淡忘；
- 事实键与新事实取代旧事实；
- 按当前聊天话题召回相关记忆；
- 所有未来主 Session 共用同一份“大肥鱼记忆”；
- 主 Session 专属 `dafeiyu_remember` 工具，由正在聊天的大肥鱼在**同一次模型思考**里语义判断并写入长期事实、约定、关系和重要经历；
- 主人手动查看、搜索、补记、删除；
- B站重要经历确定性写入，不额外启动一次“总结 AI”。

v2.4.80 起，**长期事实的含义不再由本地正则硬猜。** 每次主人发消息时，正在聊天的大肥鱼会在这一次正常模型思考里先判断：这轮是否明确出现了值得跨 Session 保存的称呼、身份、稳定偏好/厌恶、长期习惯、长期项目或状态、双方约定、关系变化、重要共同经历，或者对旧事实的明确修正。若有，她必须在最终回复前调用 `dafeiyu_remember`。这不是第二次 AI 请求，而是当前回复中的一次工具调用。

插件本地代码退到“安全闸”角色：检查记忆不能是疑问句、不能包含 `什么 / 啥 / 哪个 / 哪种 / 多少 / 谁 / 哪里 / 怎么` 等占位值、不能把模型推测当成主人事实，并负责去重和 `fact_key` 更新。同一类会变化的事实复用稳定事实键，新值会取代旧值。主人只是问“我现在最喜欢喝什么？”时，本轮只能召回已有记忆，不能反向产生一条“主人喜欢什么”的新事实。

v2.4.79 曾经用本地规则直接生成一小部分主人事实；这些旧记录升级后继续保留并在管理中心标成“v2.4.79 本地识别（旧）”。其中已经误写成疑问占位值的记录会在 v2.4.80 自动移出有效记忆，并恢复同一事实键最近的有效值。

v2.4.78 以前本插件按 Session 保存的长期记忆，在首次升级到 v2.4.79 时会自动合并进 `dafeiyu.json`；旧 Session 文件不会删除，仍保留作安全兜底。独立版 `dsh-fish-memory` 的旧数据也仍可人工导入。

这部分基于 `Yuuyuko-uu/dsh-fish-memory` 的设计与部分实现整合，并针对 Claude / Anthropic 等严格工具 schema 做了兼容处理。

### 4. 精确经历不会只靠“模型记得”

插件还会独立保存：

- 看过和挑中过的视频；
- 每轮判断与日报；
- 自己实际发出的评论和回复；
- 评论 ID / root / BV / 发送状态；
- 本地评论额度与动态额度；
- 私信与评论互动状态；
- 视频上下文缓存和诊断信息。

主 Session 需要核对细节时，可以通过只读 `bili_experience_recall` 查询自己的 B站经历档案。

### 5. 她认识人，而不是只有一个白名单

每位好友可以保存：

- UID 与昵称；
- 性格爱好；
- 和大肥鱼的关系；
- 和其他好友的关系；
- 是否允许后台私信；
- 是否允许大肥鱼主动 @；
- 是否允许对方 @ 邀请大肥鱼；
- 可标记多个“主人”作为角色关系。

社交权限和角色关系是两回事：**叫“主人”不自动获得管理权限。**

### 6. 梗与表情包也是持久化的一部分

- 梗知识库有审核状态、来源证据和别名；
- 评论、私信和 @ 回复前可以本地检索已批准的梗，不额外调用模型；
- 表情包图库支持分类、单张导入、改名、删除，以及<strong>整库 ZIP 导出 / 批量 ZIP 导入</strong>；批量导入完全保留用户自己准备好的目录结构和文件名，不逐张重命名，也不会覆盖现有同名图片；
- 表情包检索规则支持组合条件、排除词、导入导出和本地测试；
- 推荐更新规则时先导出**当前全部表情包名称 TXT + 当前规则 JSON**，把两份文件一起交给 AI 生成新的完整规则 JSON，再回管理中心导入、测试、确认后保存；这样 AI 知道真实图库里现在有哪些名字，不会凭空编文件名；
- 模型只根据安全的文件名候选选图，不会假装“看懂”没有识别过的图片。

### 7. 真正适合无人值守的安全边界

后台大肥鱼不是一个拿着整台电脑权限的普通 DSH Agent。

插件为主动值班、互动回复和独立视觉分别生成受限 overlay，并在启动前强校验。文件系统、Shell、任意 Web、子代理、工作流、Python/代码执行、会话读取等高风险能力必须关闭；异常时 **fail closed**，不会退化成裸 `headless`。

B站公开发送还有插件层硬额度、白名单、函数级校验、发送账本和人工重试限制。提示词只是辅助，真正的边界尽量放在机制层。

## 💾 她到底会长期保存什么

| 持久化层 | 保存什么 | 用来回答什么 |
|---|---|---|
| **大肥鱼身份级长期记忆** | 主人相处、约定、偏好、关系、长期状态、重要 B站经历 | “我记得我们以前……”；跨 Session 保持同一只大肥鱼 |
| **B站经历档案** | BV、视频、评论、回复、时间、状态 | “具体是哪条？我当时说了什么？” |
| **成长经验** | 表达习惯、兴趣、经历、角色关系 | “以后我应该更像怎样的大肥鱼？” |
| **好友画像** | UID、昵称、关系、兴趣和权限 | “这个人是谁？我和他熟不熟？” |
| **梗知识库** | 梗、角色、别名、证据、审核状态 | “这个梗我以前学过吗？” |
| **表情包规则** | 本地图库名称与检索关联 | “这句话有没有合适的图？” |
| **视频心愿** | 获批好友希望她找的视频方向 | “之前有人让我留意什么？” |
| **运行账本** | 配额、轮询状态、防重、发送回执 | “今天还能不能发？刚才到底成功没？” |

这些数据都尽量保存在 `%USERPROFILE%\.dsh\bili-duty\` 下，与源码目录分开。源码更新不应该清空它们。

### 完整业务备份会保存

人设、好友、成长经验、梗知识、视频心愿、**大肥鱼身份级长期记忆**、评论/私信状态、表情包检索规则、精确经历及相关 SQLite 数据。完整备份仍是一个本地 JSON 容器；JSON 本身并不存在“小到一定程度就存不下”的问题，但插件会设置单文件和总体积安全上限，避免异常数据拖垮校验与恢复。

### 大肥鱼长期记忆还有独立备份

从 v2.4.80 起，管理中心提供“单独备份大肥鱼长期记忆”。它只保存 `dafeiyu.json` 对应的身份级长期记忆，不包含当前 Session 聊天历史，也不包含 BV/rpid 等精确经历档案。恢复记忆前会先在用户指定的本机备份目录保存当前记忆快照。

推荐把它当成双保险：**完整业务备份一份 + 大肥鱼记忆专用备份一份**。这样即使未来业务数据、SQLite 和历史记录越来越多，最重要的人格连续性数据也有一份独立、容易核对和迁移的文件。

### 表情包图片单独备份

表情包图片仍不塞进业务 JSON。管理中心可直接把整个 `comment-memes` 图库导出成 ZIP，并保留文件夹层级、文件名和扩展名。批量导入 ZIP 时请先自己整理好目录与命名；插件会校验路径、图片格式、尺寸、大小和重名，采用追加式导入，拒绝覆盖已有图片。单张导入则可以在导入前直接修改分类和名称。

### 默认不会打包

- B站 Cookie / 登录凭据；
- 独立模型密钥；
- Python 虚拟环境和模型缓存；
- 视觉 Debug 图片；
- 表情包图片文件本身（请用“表情包整库 ZIP”单独导出）。

备份包含私人关系和聊天业务数据，请不要上传到公开仓库。

## 🚀 快速开始

### 环境

- DSH：`>= 0.1.7-rc.1`
- Node.js：`>= 22`
- Windows / DSH Desktop 是当前主要测试环境
- B站能力需要自己的账号扫码登录

### 安装

DSH Desktop：

```powershell
dsh plugin --profile desktop add github:minedalang/dsh-dafeiyu-life
```

Web profile：

```powershell
dsh plugin --profile web add github:minedalang/dsh-dafeiyu-life
```

安装后请**完全退出并重启 DSH**。

### 第一次设置

进入 **设置 → 大肥鱼**：

1. 点击 **装主依赖**，建立插件自己的 Python 环境；
2. 点击 **扫码登录**，登录你自己的 B站账号；
3. 新建或选择一个你准备长期和她聊天的 DSH 会话；
4. 打开 **大肥鱼管理中心 → 大肥鱼的家**，把这个会话设为主 Session；
5. 开启 **大肥鱼跨 Session 长期记忆（身份级）**；
6. 回到设置页开启 **大肥鱼总开关**；
7. 按需要开启 **自定义时段自动刷**；
8. 先跑一两轮确认日报、评论和记忆都符合你的预期，再逐步打开公开互动。

以后你的日常用法可以非常简单：**让主 Session 一直作为“大肥鱼的家”，后台自动生活照常跑。**

## 🏠 大肥鱼管理中心

设置页只保留高频开关；复杂配置集中到管理中心。

主要页面包括：

- **大肥鱼的家**：主 Session（当前房间）、经历同步、跨 Session 身份级长期记忆、精确经历档案；
- **人设与好友**：人设、好友画像、关系与权限；
- **最近评论**：公开评论、楼中楼、发送状态和人工核查；
- **后台私信**：聊天、白名单和视频心愿；
- **成长记忆**：表达习惯、兴趣、经历和关系审核；
- **梗知识库**：梗条目、来源证据、审核；
- **表情包管理**：图库和检索规则；
- **次数与额度**：视频、评论、私信、视觉、表情包等限制；
- **后台轮询**：私信、评论回复、@ 邀请、热门评论检查；
- **每日报告 / 每日诊断**：看她做过什么，以及哪里出了问题；
- **数据备份**：本地完整业务备份与恢复。

## 🔐 关于自动评论和隐私

这个项目可能代表你的 B站账号公开发言，因此默认设计偏保守：

- 不必要的公开互动默认关闭；
- 评论、私信、@、动态均有独立开关和限制；
- AI 可以决定沉默；
- 评论区、字幕和简介都视为外部不可信输入；
- 后台 Agent 不允许任意读取 DSH 会话、工作区和本机文件；
- 主 Session 桥只连接主人明确选择的会话，不会“找不到就随便挑一个”；
- 陌生人私信正文默认不会被当成长期人格记忆灌进主 Session。

这不是一个“开了就绝对不会说错话”的系统。公开互动前仍建议先用私信模式或较低额度观察一段时间。

## 🔄 从旧的 `dsh-bili-scroll-plus` 迁移

当前用户很少，因此从这一版开始直接使用新的包名和插件 ID，不再长期维护旧名称兼容层。

如果你正在使用旧版，推荐这样迁移：

1. **旧插件里先做一次“备份数据”**，记住备份 JSON 所在文件夹；
2. 完全退出 DSH；
3. 移除旧包：

```powershell
dsh plugin --profile desktop remove dsh-bili-scroll-plus
```

4. 安装新包：

```powershell
dsh plugin --profile desktop add github:minedalang/dsh-dafeiyu-life
```

5. 完全重启 DSH；
6. 进入 **设置 → 大肥鱼**，确认插件加载；
7. 当前版本仍沿用 `%USERPROFILE%\.dsh\bili-duty\` 作为业务数据目录，因此本机原有业务文件通常会直接接上；
8. 如果 DSH 配置因为插件 ID 改名没有继承，先在「数据备份」重新**确认备份目录**，再选择旧 JSON 执行恢复；
9. B站登录凭据不在业务备份里，如登录状态没有沿用，请重新扫码；
10. 如果以前单独装过 `dsh-fish-memory`，不要让它和“大肥鱼身份级长期记忆”同时向当前主 Session 注入记忆。可先卸载旧插件，再在「大肥鱼的家」按当前主 Session 导入旧记忆文件；导入后会进入统一的 `dafeiyu.json`。

旧格式 `dsh-bili-scroll-plus-backup` 的业务备份仍可被新版本读取，新的备份会写成 `dsh-dafeiyu-life-backup`。

## 🧭 能力边界

- 低清预览帧不等于完整视频理解；
- B站 API、风控和客户端页面行为可能变化；
- 评论跳转不能保证 B站前端每次都精确滚到目标楼层；
- 本地转写、视觉模型和不同 Provider 的实际能力取决于用户环境；
- 项目仍处于快速迭代阶段，升级前建议先做业务备份。
